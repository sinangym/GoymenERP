# Manual receipt preparation contract v1

Source: PR #254, 6f0cd10259aeb2a44d32a92535464ed2ce096cf7, FINANCE_MANUAL_SOURCE_JIT_SPEC_v1.md sections 2-5; issue #66 comment 5653637829.

All examples are SENTETIK/NOT_ENV. UUIDs, profile scale/range and versions are synthetic test inputs, never registry entries or grants. Use FinanceJson.CreateOptions for this proposed JSON shape. No HTTP routes/status mappings or platform 403 error code are published here.

FS0 is the authorized Finance bank reader port. FS1 preparation has no balance or financial effect. DraftSave is full replacement (not PATCH); create omits identity/version using null, update requires both. Record resolves the persisted draft and current version. Reverse resolves the original source and its account/currency/amount; client supplies only identity/version/date/reason. List/detail and successful resources bind server company/source identity. A Succeeded Draft resource means only draft persistence, never financial recording.

Runtime implementation must validate fresh authority (including replay and amount disclosure), owner account eligibility, actual currency/profile and period. PreparationValidator only validates supplied owner snapshots; an empty issue list grants no permission and proves no persisted financial effect. Roles0 is accepted by the party eligibility port; Finance does not impose a Counterparty role bit.

Missing runtime: authenticated context adapter, bank projection, Counterparty adapter, Settings profile provider, period provider, Identity action/grant mapping including OPEN-009, persistence, atomic audit/idempotency/financial event terminal, source number issuance, linked reversal enforcement, official allocation calculator and source state transitions. These ports intentionally have no successful default implementation. Allocation unavailability stays null/unavailable. Server responses must redact money before serialization, not merely hide it in UI. Record/reverse must recheck allocation knowledge and reject allocated reversals in this narrow slice.

A successful replay preserves resource and originalCorrelationId and sets isReplay=true after fresh authority checks. Unknown transport outcome keeps the same idempotency key, company, actor and payload. Same key/different payload conflicts. Success followed by failed GET does not resubmit Record. Request metadata is separate from body; the host adapter binds server actor/company/correlation/causation and the submitted idempotency key.

No API/DB write, shared DI/OpenAPI/permission registry/CI integration, SQL/browser/ENV_READY or K3 acceptance is claimed. Pure tests are run independently via tests/GoymenERP.Finance.UnitTests/GoymenERP.Finance.UnitTests.csproj. Runtime implementation and money/migration/permission/cross-module K3 gates remain separate.

Settings alignment: PR #256 @ 5e0c5502ff4d715f5f3e0579beb3a49f8e5b13e0 is the sole prerequisite source. Finance references Settings.Application directly; local IMoneyProfilePort/IFinancePeriodPort/MoneyProfile were removed. The consumer uses MoneyProfileV1, PeriodEligibilityV1 and ExactPositiveDecimalV1. Shared decimal errors replace the earlier local lexical/scale error names. settings_access_denied and settings_provider_unavailable propagate distinctly. The host must supply the approved operation mapping and authenticated Settings provider scope.
