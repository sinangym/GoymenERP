Business comment #254/5654539215 assigns operation/route/status/replay/permission technical mapping to existing Backend owners without a new human business decision. Finance therefore pins the Settings lookup key FinanceMoneyOperations.ManualBankReceiptV1 = finance.manual-bank-receipt.v1. This key selects no currency, scale, effective dates, grant or period policy; the Settings owner must still return approved profile data for the exact company/currency/date/key. The central IFinanceDraftReadBinding must return this constant instead of null. Permission and bank adapters remain unavailable, so default runtime still returns 503 without fabricating a usable context.

DraftReadContextReader.GetAsync(DraftReadContextRequest request, string? acceptedMoneyOperation, string correlationId, CancellationToken cancellationToken) is implemented in Finance.Contracts. Company and actor come from ICompanyContext/ICurrentUser; no body/query company, actor, currency, profile or label is trusted. The operation argument must come from an accepted server mapping. Null mapping fails unavailable. The existing IFinancePermissionPort.ReadBankAccounts action gates this read and is rechecked before response disclosure; it is not an Identity grant name. The existing IFinancePartyAccountPort supplies PartyAccountEligibility with Label (DraftPartyLabel) and IsPartyActive; the central API adapter must call Counterparty.GetAuthorizedPartyAsync and select the exact active company account, including valid roles0. Missing labels or inactive metadata never produce a context. Finance has no Counterparty project reference. Settings.GetMoneyProfileAsync supplies currency code and effective profile for the selected bank currency and occurredOn. Response contains no amount, balance, source posting, approval or write capability.

Published route (central contribution edbdf8d; OpenAPI operation GetFinanceManualReceiptDraftContextV1): GET /api/v1/finance/manual-receipts/draft-context?treasuryAccountId=<uuid>&partyId=<uuid>&companyAccountId=<uuid>&occurredOn=YYYY-MM-DD. All four query fields are required. Selected bank currency is authoritative. occurredOn accepts exactly ISO 8601 yyyy-MM-dd (FinanceIsoDate); month-first, unpadded, named-month, space-padded or time-bearing forms are a code-less 400 and never reach the reader (ORG #261 P2-A). Serialize only Resource on success, using FinanceJson.CreateOptions semantics; do not serialize internal outcome/code envelopes as success. Required nullable fields remain present. No request body and no idempotency key/replay headers are required for this read.

Outcome mapping for central implementation:

| Consumer outcome | HTTP | Wire body |
|---|---|---|
| Found | 200 | Non-null DraftReadContextView with company/date/bank/currency/profile/party identity |
| InvalidRequest / invalid query binding | 400 | Central validation problem; no partial resource |
| Denied | 403 | Existing platform problem code forbidden |
| NotFound | 404 | Central not-found problem; no cross-company label disclosure |
| Unavailable | 503 | Existing platform problem code service_unavailable; never empty200 or zero balance |
| Unauthenticated middleware | 401 | Existing platform problem code authentication_required |
| Unexpected exception | 500 | Existing platform problem code internal_error |

The current main API Errors/ErpProblemCodes.cs and ErpProblemDetailsExtensions.cs actually define/normalize forbidden and service_unavailable. Internal settings_access_denied and settings_provider_unavailable remain distinct consumer outcomes but must not be promised as 403/503 wire codes because the platform writer normalizes those responses. Internal finance_* diagnostic codes in DraftReadContextResult are not new entries in the shared public problem-code registry. The 400/404 bodies stay code-less. Missing sources, exactly:

- Finance bank owner: the persisted source implementing IFinanceBankAccountReader is FS0's `FinanceBankAccountService` (Finance.Infrastructure; see the module README). The host does not register it yet, so the host's UnavailableFinanceBankAccountReader still returns unavailable (or denied for wrong company/actor), never an empty catalog success.
- Settings owner: ISettingsPrerequisiteProvider exists, but accepted company/currency/code/profile ID/version/scale/effective-date data does not. The host now registers ApprovedSettingsPrerequisiteProvider; it approves unit profiles only, and its money-profile and period reads (the only ones Finance makes) still answer exactly as the unavailable adapter did (settings_provider_unavailable), so this read stays unavailable.
- Identity/Business owner: no accepted Finance read grant/action mapping or manual-receipt MoneyProfile operation identifier exists. The supplied UnavailableFinancePermissionPort never grants access; central may register this adapter until an accepted mapping arrives. Read metadata preparation does not resolve OPEN-009.

No second catalog, seed data, grant, role, operation constant, period-open fallback or database write is introduced. Central can expose an honest unavailable read contract without asserting that a user can prepare/save real bank receipts.

A future persistent DraftSave must use the platform transaction/audit/terminal behavior and pinned concrete status mapping; this change does not fabricate a generic Finance command executor or publish Record/Reverse endpoints. Existing preparation CommandResult remains a model, not an HTTP execution receipt. Unknown command outcomes retain the same key/company/actor/payload; a successful read context is never a command replay or financial success.
